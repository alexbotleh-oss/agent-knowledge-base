# Задание агенту чата: сбор и пополнение общей памяти

Эта инструкция предназначена для нового чата, который получает архивы, чаты, файлы и результаты работы и должен пополнять `alexbotleh-oss/agent-knowledge-base`.

## Главная цель

Восстановить доступный опыт с максимально возможной доказательностью, сохраняя исходные данные, связи и неопределённость. Не начинать с переписывания всей истории каждый раз: продолжать существующий реестр, сверять новые материалы с уже собранными и добавлять только новые факты, связи, уточнения и исправления.

## Перед началом

1. Прочитать `core/repository_scope.md`, `core/universal_instructions.md`, `core/memory_model.md`, `core/source_ingestion_protocol.md`, `core/chronology_reconstruction.md` и `core/memory_registry_and_multidimensional_index.md`.
2. Восстановить актуальную ветку, PR, HEAD, состояние проверок, существующие записи и handoff. Не предполагать, что локальная или чатовая память актуальнее репозитория.
3. Уточнить область текущего сбора: универсальный опыт или конкретный `PROJECT_ID`. Не переносить проектные факты в универсальные уроки без доказанной переносимости.
4. Зафиксировать baseline: какие архивы/файлы доступны, их размеры/hash, coverage и отсутствующие источники. Не заявлять полноту, если она не доказана.

## Приём данных

1. Сохранять RAW неизменяемым и регистрировать каждый архив отдельным `archive_id`/snapshot.
2. Извлекать исходные message IDs, node IDs, parent/child, временные метки, роли, текстовые части, типы содержимого и ссылки на вложения. Не представлять недоступное вложение как изученное.
3. Разделять `event_time`, `source_time` и `recorded_at`; сохранять исходное время и точность.
4. Создавать стабильные адреса источника; никогда не ссылаться на номер строки/позицию, способную сдвинуться.
5. Импортировать сначала в staging. Проверить дубли, коллизии ID, пробелы в датах, конфликтующие версии, полноту ветвей и повторный импорт.
6. Сопоставить с существующими данными. Повторный импорт должен быть идемпотентным; найденное подтверждение добавляется как источник, а не как бессмысленная копия записи.
7. Если новый архив уточняет старое событие, сохранить прежнее представление и создать ревизию/связь `supersedes`; если связь с источником неоднозначна — не переназначать автоматически.
8. Не загружать приватный архив в публичный репозиторий без прямого разрешения пользователя. В репозиторий записывать только необходимые структурированные выводы и безопасные ссылки/идентификаторы.

## Извлечение и классификация

Каждую запись классифицировать по нескольким независимым измерениям, когда применимо:
- проект и задача;
- контекст/этап и связанные сообщения;
- тип: событие, решение, положительный опыт, отрицательный опыт, гипотеза, проверка, ошибка, исправление, вопрос, handoff;
- время события, время исходного источника, время записи;
- тема/теги;
- статус решения: предложено, принято, отклонено, пересмотрено, отменено;
- статус доказательств: reported, observed, inferred, verified, unknown;
- статус записи: candidate, accepted, disputed, superseded, deprecated;
- ссылки на первичные источники, связанные записи и уверенность.

Одна запись может иметь несколько меток и участвовать в разных сортировках без копирования содержания. Не путать отрицательный результат с ошибкой агента, а пользовательское решение — с предложением агента.

## Повторные ошибки и отсутствующий опыт

1. Для каждого важного урока найти исходную причину его появления и извлечь поисковые признаки: симптом, действие, ожидаемый результат, фактический результат, исправление, ограничения и временной диапазон.
2. Искать в доступной истории назад и вперёд, по тексту, времени, ветвям диалога, файлам/версиям и связанным событиям.
3. Разделять сообщения об одном инциденте и отдельные повторные инциденты. Совпадение слов не доказывает совпадение причин; временная близость не доказывает причинность.
4. Сопоставить каждый подтверждённый эпизод с существующими записями: covered / partly_covered / missing / disputed.
5. Предложить пропущенные записи с источниками и обоснованием; не добавлять автоматически непроверенные кандидаты в confirmed memory.
6. Сохранять отрицательные попытки и регрессии даже после исправления; общий урок может связывать несколько отдельных инцидентов.

## Сортировки и поиск

Реестр должен позволять получать представления по контексту, задаче, проекту, времени, типу знания, теме, решениям, положительному/отрицательному опыту, инцидентам, статусу проверки и происхождению. Эти представления — запросы к одной связанной модели, а не отдельные независимые копии каталогов.

Минимальные направления поиска:
- контекст → сообщение → время/архив;
- время → сообщение → контекст ветви;
- урок/причина → все похожие эпизоды → пропуски журнала;
- решение → исходное решение пользователя → реализация → проверка/откат;
- новый архив → существующие записи → новые сведения/дубли/конфликты.

## Безопасность изменений

- Не удалять существующий опыт ради удобства или потому, что новый импорт выглядит полнее.
- Не перезаписывать RAW.
- Не переназначать ссылки по позиции.
- Любое изменение идентификаторов и ссылок фиксировать в таблице переадресации с методом, уверенностью и статусом проверки.
- Хранить журнал импорта, список изменений, проверку целостности и возможность отката.
- Если данных недостаточно, продолжать доступную часть работы, отмечать пробелы и не утверждать, что восстановление полное.
- Не считать валидатор PASS доказательством смысловой полноты; не заявлять CI PASS без реального запуска/результата.

## Выход каждого этапа

Записать в репозиторий:
1. manifest источников и границы покрытия;
2. новые/уточнённые события, решения и уроки со стабильными IDs и provenance;
3. найденные повторы, кандидаты на пропуски и их статусы;
4. конфликты и нерешённые вопросы;
5. результаты тестов, проверки связей, import diff и rollback reference;
6. обновлённые PROJECT_STATE/TASK_STATE/HANDOFF и следующий конкретный шаг.

Цель — не создать видимость идеальной полноты, а сделать память расширяемой, обратимой, проверяемой и пригодной для дальнейшего обогащения.
