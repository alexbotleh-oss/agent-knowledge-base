# Протокол приёма и аудита источников опыта

## Назначение

Обеспечить воспроизводимое извлечение контекста из экспортов чатов, файлов и артефактов, поступающих частями. Ни один список файлов, архив или сводка не считается полным только по названию или по совпадению количества сообщений. Этот протокол применяется до переноса сведений в проектную память и при каждом новом поступлении источников.

## Разделение слоёв

1. **RAW — исходник.** Сохранять полученный файл без изменений, фиксировать имя, размер, доступный хеш, формат и источник/дату получения. Не редактировать единственную копию.
2. **INVENTORY — инвентаризация.** Список файлов из манифеста, содержимое архивов, индексы имён вложений и фактически доступные файлы учитывать отдельно.
3. **EXTRACTED — извлечённое содержание.** Сообщения, временные метки, IDs, текст, ссылки на вложения и метаданные сохранять с указанием точного источника.
4. **CANDIDATE — кандидат на память.** События, решения и уроки сначала считать кандидатами; классифицировать проект, время, доказательность и уверенность.
5. **CANONICAL — подтверждённая память.** Вносить после проверки происхождения, дубликатов, конфликтов, принадлежности проекту и статуса доказательств.

Не подменять один слой другим. Строка-маркер вложения в сообщении не доказывает, что само вложение доступно или изучено.

## Приём экспорта: обязательный алгоритм

1. **Зафиксировать входы.** Перечислить все отдельно полученные архивы, JSON, HTML, манифесты, индексы имён и отдельные бинарные вложения. Не считать, что один ZIP содержит файлы, лежащие рядом в исходной папке.
2. **Осмотреть архивы без предположений.** Получить перечень внутренних путей и размеров; отдельно отметить вложенные архивы, ошибки чтения и повторяющиеся пути.
3. **Разобрать манифест.** Посчитать записи и суммарный заявленный размер; определить обязательные файлы, типы файлов и дубли путей. Сверить манифест с фактически доступными файлами. Отсутствующий файл означает «не получен/не доступен», а не автоматически «потерян».
4. **Сопоставить индексы.** Для каждого индекса имён проверить ключи относительно манифеста; отдельно указать, является ли индекс полным каталогом или только таблицей соответствий. Не трактовать разницу размеров двух индексов как пропажу файлов без подтверждения семантики формата.
5. **Извлечь сообщения.** Подсчитать объекты диалогов, сообщения, уникальные IDs, роли, диапазон дат и маркеры вложений. Записывать метод подсчёта и критерий уникальности. Не смешивать «объекты диалогов», «узлы сообщений», «уникальные IDs» и «экспортные файлы».
6. **Проверить полноту независимо.** Сверить статистику JSON с HTML-представлением, манифестом и другими доступными источниками, когда они реально доступны. Не считать совпадение числа сообщений доказательством полноты диалогов. Если заявлено 74 диалога, а получено 37 объектов, оставить расхождение открытым до объяснения.
7. **Проверить вложения по приоритету.** Сначала инвентаризировать все вложения; затем проверять вложения, на которые ссылаются ключевые решения, правки кода, ошибки, скриншоты UI и результаты тестов. Для каждого указать: байты доступны/недоступны, содержимое изучено/не изучено, выводы, ограничения. Не заявлять аудит вложения по одному имени файла или текстовому маркеру.
8. **Извлечь события по атомарным утверждениям.** Одно событие — одно наблюдение, решение, изменение или результат. Смешанные разговоры раскладывать по проектам и сообщениям, а не назначать целиком одному проекту.
9. **Разрешить происхождение и хронологию.** Хранить conversation ID, title, message ID, timestamp исходного сообщения, event_time (если известен), время импорта и ссылку/путь к артефакту. Порядок импорта не является порядком событий. При неизвестном времени использовать unknown/диапазон, не угадывать.
10. **Дедуплицировать без потери доказательств.** Совпадающие по смыслу события могут объединяться, но каждый независимый источник добавляется к записи. Не объединять разные версии файлов или разные проектные цепочки только из-за одинакового названия.
11. **Сохранять конфликт.** Если источники расходятся, записать оба значения, их происхождение и способ возможной проверки. Не «исправлять» расхождение молча и не повышать уверенность из-за повторения одной и той же сводки.
12. **Сформировать отчёт полноты.** Для каждого набора источников указать: ожидается по манифесту; фактически получено; разобрано; содержимое проверено; не получено/не читается; не проверено; дубли; ошибки; расхождения; границы выводов.
13. **Только затем обновить память.** Сохранить события/уроки, обновить актуальное состояние и handoff, выполнить валидацию ссылок, схем, уникальности IDs и проектных границ.

## Статусы доказательств

- reported — пользователь или источник сообщает о факте, но первичная проверка отсутствует.
- observed — факт непосредственно виден в предоставленном артефакте/сообщении.
- verified — вывод подтверждён воспроизводимой проверкой или первичным доказательством, пригодным для этого вывода.
- inferred — разумный вывод из нескольких сигналов, но прямого подтверждения нет.
- unknown — данных недостаточно.
- Для полноты набора использовать отдельно: COMPLETE, PARTIAL, UNKNOWN. Наличие всех перечисленных файлов в манифесте не означает, что их байты доступны или содержание изучено.

## Защита от ложной уверенности

- Манифест подтверждает заявленный состав экспорта, но сам по себе не доказывает, что все файлы были переданы агенту.
- Архив подтверждает только фактически перечисленные внутри него элементы.
- Индекс имён подтверждает только описанную им связь имён.
- Сообщение о вложении не заменяет само вложение.
- Скриншот подтверждает только видимое состояние в конкретном моменте; он не доказывает работоспособность невидимых функций.
- Успешная структурная валидация доказывает корректность проверенных структур, но не полноту истории и не корректность смысловой классификации.
- Если доказательства неполны, продолжать доступную часть работы, но не объявлять архив или память полными.

## Минимальный отчёт аудита

- Идентификатор/название набора и источник.
- Список реально полученных входов с размерами и хешами, если доступны.
- Формат и содержимое архивов.
- Заявленный и фактически обнаруженный состав.
- Количество диалогов, сообщений и уникальных ID с методикой подсчёта.
- Вложения: количество по индексу, доступные байты, просмотренные артефакты.
- Необъяснённые расхождения и гипотезы, явно помеченные как гипотезы.
- Что можно утверждать; что нельзя утверждать.
- Выполненные проверки, результаты, следующий шаг.

## Быстрый возобновляемый импорт (без смыслового анализа на лету)

### Цель и граница этапа

Импортёр отвечает за **сохранение исходной истории и восстановление позиции**, а не за извлечение всех знаний. Во время первичного импорта не выполнять семантическое объединение ошибок, обобщение уроков, причинно-следственную интерпретацию или построение поисковых индексов. Эти операции выполняются отдельным последующим проходом по сохранённым данным. Это снижает время обработки и риск потери хронологии из-за преждевременного обобщения.

### Состояния импорта

Каждый запуск имеет стабильный `import_id` и отдельную запись состояния:
- `REGISTERED` — источник зарегистрирован, ожидаемый состав ещё не проверен;
- `SNAPSHOTTED` — исходный файл сохранён без изменений, известны размер и доступная контрольная сумма;
- `INVENTORIED` — перечислены диалоги/сообщения/вложения, записаны счётчики и диапазоны;
- `STAGING` — исходные записи порциями сохраняются в промежуточное хранилище;
- `PAUSED` — обработка остановлена или прервана; следующий курсор записан;
- `RAW_COMPLETE` — все доступные исходные записи сохранены и сверены с ожидаемым составом источника;
- `PARTIAL` — сохранена только часть или есть неразрешённые расхождения;
- `FAILED` — зафиксирована ошибка, возобновление требует проверки её причины.

Статус `RAW_COMPLETE` означает полноту только относительно конкретного полученного снимка и правил парсера; он не доказывает полноту всех чатов/вложений, перечисленных во внешнем манифесте.

### Пакеты, курсор и безопасный повтор

1. Сохранять оригинал целиком до разбора, если среда позволяет; не изменять единственную копию.
2. Разбирать источник потоково или порциями ограниченного размера. Размер пакета настраиваемый; начать с небольших порций и подобрать его по измеренному времени/объёму, а не считать фиксированное число сообщений универсальным.
3. Для пакета сохранять диапазон исходных ID/позиций, число записей, хеш входного фрагмента (если вычислим), версию парсера, результат и ошибки.
4. Записывать результаты в staging транзакционно: сначала данные пакета, затем подтверждение фиксации и продвижение курсора. Не отмечать пакет завершённым до подтверждения устойчивой записи.
5. Курсор привязывать к устойчивым исходным ID/ключам, а не только к номеру строки или смещению, которое может измениться при новом экспорте. Если стабильного ID нет, использовать составной локатор в пределах неизменяемого снимка.
6. Повторный запуск должен быть идемпотентным: уникальный ключ исходной записи включает `archive_id + conversation_id + source_message_id/source_node_id` (с пространством имён и fallback только внутри конкретного снимка). Повтор уже сохранённой записи не создаёт второй экземпляр и не стирает прежнюю ревизию.
7. Если подтверждение записи потеряно из-за разрыва соединения, при возобновлении сначала проверить наличие и хеш пакета в staging. Только затем повторить отсутствующую операцию.
8. После каждого успешно зафиксированного пакета обновлять локальную контрольную точку и журнал событий. Удалённую синхронизацию выполнять отдельно; недоступность сети не должна стирать локально подтверждённый прогресс, если локальное устойчивое хранилище существует.
9. При отсутствии локального хранилища не заявлять защиту от разрыва/закрытия сеанса: требуется сначала создать доступный устойчивый пункт сохранения или уменьшить объём одного шага.

### Минимальные артефакты для возобновления

- `IMPORT_MANIFEST`: снимок источника, размер/хеш, формат, ожидаемые и обнаруженные счётчики, версия парсера.
- `IMPORT_STATE`: состояние, последний подтверждённый пакет, устойчивый курсор, текущая ошибка, следующий шаг, версии схемы и парсера.
- Append-only `IMPORT_EVENTS`: начало/завершение пакета, успешная фиксация, пауза, ошибка, возобновление и проверка — с временными метками и ссылкой на пакет.
- `STAGING`: исходные сообщения и метаданные в исходном порядке, без смыслового объединения.
- `GAP_REGISTER`: недоступные/нечитаемые источники, сообщения и вложения, а также необъяснённые расхождения.

Это логические роли, а не обязательные отдельные файлы: их можно реализовать в SQLite/другом устойчивом хранилище или согласованном наборе файлов. В первой версии выбирать минимальную структуру, которая поддерживает транзакционную запись, уникальные ключи и восстановление курсора.

### Разделение времени и причинности

Импортёр сохраняет исходные ID, исходные временные метки, родительские/ответные связи, порядок элементов в экспорте и ссылки на вложения. Он не выводит причинность из простого соседства сообщений. Последующий анализ строит отдельные события и связи `caused_by` только при наличии доказательств; иначе записывает гипотезу/неизвестность. Семантическое объединение не удаляет исходные сообщения или отдельные эпизоды.

### Проверки перед статусом RAW_COMPLETE

- Все записи, доступные в полученном снимке, перечислены и разобраны либо каждый пропуск явно записан.
- Количество диалогов, сообщений и уникальных исходных ID сверено по задокументированной методике.
- Нет неразрешённых ошибок парсинга, скрытых за статусом завершения.
- Все пакеты, отмеченные завершёнными, реально присутствуют в staging и проходят проверку целостности.
- Повторный запуск того же снимка не меняет количество уникальных исходных записей и не уничтожает ревизии.
- В контрольной точке указаны следующий курсор и все открытые расхождения.

### Минимальные испытания механизма

1. Искусственно прервать импорт после подтверждённого пакета и возобновить его; ранее сохранённые данные должны совпасть по ключам/хешам.
2. Повторно запустить уже импортированный снимок; число уникальных исходных записей не должно измениться.
3. Смоделировать ситуацию «данные записаны, подтверждение потеряно»; возобновление должно проверить staging до повтора.
4. Передать контрольную точку новому процессу/агенту; он должен продолжить с сохранённого курсора, не полагаясь на память предыдущего чата.
5. Сверить хронологию и ссылки на источники после импорта; смысловой анализ на этом этапе не требуется.

До прохождения этих испытаний протокол описывает требуемое поведение, но не является доказательством, что конкретная реализация уже его обеспечивает.


## Исполняемый прототип: `tools/resumable_chat_import.py`

Первый runtime-прототип добавлен отдельно от существующего генератора производных записей `tools/archive_registry_staging.py`. Он предназначен для локального первичного сохранения, а не для смыслового анализа.

### Что делает прототип

- Считает SHA-256 и размер исходного JSON/ZIP; сохраняет неизменяемую копию в `<out>/snapshots/<sha256>.<ext>` и проверяет её целостность.
- Потоково читает верхний JSON-массив, декодируя по одной беседе, а не загружая весь экспорт в память. Для ZIP ожидает ровно один файл с basename `conversations.json`.
- Сохраняет полный структурный объект беседы в SQLite как непрозрачный JSON payload; вложенные сообщения, узлы mapping, родительские/дочерние ссылки и исходные поля не превращаются в краткое резюме. Точная байтовая копия источника остаётся в snapshot.
- Фиксирует порцию исходных записей, курсор и событие журнала одной транзакцией SQLite (`WAL`, `synchronous=FULL`). Повторная запись идентичного локатора не создаёт дубликат.
- Ведёт состояние импорта, число подтверждённых бесед, ошибки и append-only события; повтор запуска с теми же источником, каталогом и `archive_id` возобновляет незавершённый импорт.
- Сохраняет локально; сетевой доступ и загрузка пользовательского содержимого в GitHub не требуются.

### Запуск

```bash
python3 tools/resumable_chat_import.py /path/to/conversations.json \\
  --out /path/to/local-import-state --archive-id CHAT-EXPORT-2026-10-14 \\
  --batch-size 100

# ZIP-экспорт поддерживается тем же способом:
python3 tools/resumable_chat_import.py /path/to/export.zip \\
  --out /path/to/local-import-state --archive-id CHAT-EXPORT-2026-10-14
```

Для имитации прерывания в тестах доступен скрытый CLI-параметр `--stop-after-batches`; он не предназначен для обычного запуска.

### Границы и критерии готовности

- Это первый исполняемый vertical slice, а не доказательство полноты всей истории чатов. Статус `RAW_COMPLETE` означает, что все беседы в конкретном снимке JSON разобраны и сверены по количеству с SQLite. Полнота внешних вложений и внешнего списка чатов остаётся отдельной проверкой.
- В SQLite сохраняется структурный JSON объект беседы; отдельный нормализованный индекс сообщений и извлечение бинарных вложений не выполняются. Последующий анализатор должен читать исходные payload и создавать производные записи с provenance.
- Возобновление использует сохранённый байтовый offset внутри декодируемого `conversations.json` (для ZIP — внутри этого ZIP-member), следующий ordinal и последний подтверждённый source locator. Offset хранится в записи импорта, ключ которой включает SHA-256 всего исходного снимка; он не переносится на другой снимок. В SQLite в одной транзакции с пакетом сохраняется offset конца последней беседы. Старые записи без offset безопасно переходят через повторное сканирование от начала. Для ZIP реальная скорость `seek` зависит от поведения `ZipExtFile` и должна измеряться на больших архивах.
- До использования на единственной копии данных следует испытать прерывание, повтор, повреждённый JSON, ZIP, потерю подтверждения и передачу контрольной точки новому процессу. Локальный runtime-тест и CI для точного HEAD должны быть зелёными; только документация PASS не считается.
