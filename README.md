# agent-knowledge-base

Общая база опыта и протокол непрерывной контекстно-целевой работы агента ChatGPT между чатами и проектами.

**Границы названий:** этот репозиторий называется `agent-knowledge-base`. ORGANISM и другие пользовательские проекты ведутся как отдельные проектные цепочки внутри общей системы памяти; они не являются альтернативными названиями репозитория. Все изменения инфраструктуры памяти и универсальных протоколов относятся к `agent-knowledge-base`. См. [`core/repository_scope.md`](core/repository_scope.md).

## Назначение
- Накапливать проверяемый положительный и отрицательный опыт из реальных проектов.
- Восстанавливать цель, договорённости, события и состояние задачи при переходе в новый чат.
- Давать агенту возможность самостоятельно строить цепочку действий из намерения пользователя, контекста, ограничений и состояния проекта.
- Исключать циклы «правка ИИ → проверка пользователя» за счёт автономного выбора следующего шага и проверки доступными средствами.
- Сохранять отдельную цепочку событий каждого проекта при повторном использовании общих переносимых уроков.
- Делать визуальную диагностику и функциональную регрессию частью проверки UI-задач.

## Память проекта
Для каждого проекта использовать шаблоны из `templates/`:
- `project_state.md` — актуальная цель, состояние и следующий шаг.
- `task_state.md` — цель текущей задачи, критерии, выполненное и оставшееся.
- `event_record.jsonl.example` — формат событий.
- `lesson_record.jsonl.example` — формат уроков.

В самом проекте поддерживать PROJECT_STATE.md, TASK_STATE.md, EVENT_LOG.md, DECISIONS.md, LESSONS.md и HANDOFF.md. Журналы событий преимущественно дополняются новыми записями; текущий снимок состояния обновляется со ссылками на подтверждающие события.

## Структура
- `core/` — универсальные инструкции и политики.
- `projects/<PROJECT_ID>/` — контекст, решения, уроки и состояние конкретного проекта.
- `schemas/` — зарезервировано для формальных схем памяти.
- `examples/` — только реальные кейсы с происхождением и проверяемыми уроками.
- `stacks/<stack>/{lint,test,build}.sh` — адаптеры Flutter, Flet, Python, Java, HTML/PWA, C++, C#, Rust, JavaScript и Go.
- `tools/validate_project.sh` — проверки репозитория и обнаруженных стеков.
- `tools/validate_memory.py` — структурная проверка протокольных файлов и примеров записей памяти.
- `tools/generate_report.sh` — отчёт о проверках.
- `.github/workflows/validate.yml` — CI.

## Проверенный исполнитель действия

- [Практический runbook](docs/verified_task_executor.md) для `tools/verified_task_executor.py`: синтетический сквозной тест, dry-run, явное выполнение и проверка повторного извлечения сохранённого результата. Исполнитель не является песочницей и не запускается автоматически из ChatGPT.

## Запуск проверок
```bash
chmod +x core/*.sh tools/*.sh stacks/*/*.sh
python3 tools/validate_memory.py
python3 -m unittest discover -s tests
tools/validate_project.sh /path/to/project
tools/generate_report.sh /path/to/project
```

Адаптеры не устанавливают зависимости автоматически. Отсутствующий инструмент отмечается как SKIP; `STRICT_VALIDATION=1` превращает пропуск обязательной проверки в ошибку. Наличие адаптера не доказывает, что тесты существуют или визуальная проверка выполнена.

## Обязательное поведение агента
1. В начале задачи восстановить актуальную память и сверить её с доступным фактическим состоянием.
2. Самостоятельно определить этапы, зависимости, критерии готовности и проверки; не заставлять пользователя расписывать очевидную последовательность.
3. Использовать общие уроки только после проверки применимости; не смешивать проектные факты.
4. После существенной работы сохранять события, решения, результаты, неудачные попытки и handoff.
5. Для UI по возможности запускать приложение, получать скриншоты, проверять адаптивность, переполнение и действия. Если браузер/рендерер недоступен, указывать VISUAL=SKIP/BLOCKED с причиной.
6. Не объявлять PASS без выполненной проверки и доказательств.
7. Не создавать бесконечные повторные циклы: при неудаче установить причину и изменить подход; спрашивать пользователя только при реальном блокере или решении, которое принадлежит ему.

## Важное ограничение
Репозиторий является внешней памятью и протоколом, но не изменяет параметры модели ChatGPT и сам по себе не гарантирует автоматическое чтение файлов каждым новым чатом. Рабочая среда агента должна подключать репозиторий/файлы или позволять агенту получить их доступными инструментами. Если доступа нет, агент должен сообщить об этом и запросить минимально необходимый способ подключения.

- [Единый реестр памяти и многомерный поиск](core/memory_registry_and_multidimensional_index.md) — связанная модель, устойчивые адреса, сортировки и безопасное пополнение.
- [Инструкция агенту чата по сбору памяти](core/chat_memory_collection_task.md) — рабочий протокол восстановления, извлечения, сверки и дополнения опыта.


## Приём источников: текущая исполняемая часть

Для локального тестового/рабочего снимка доступны следующие отдельные шаги:

- `tools/archive_registry_staging.py` — структурный staging исходного экспорта.
- `tools/adapt_archive_staging_to_intake.py` — создание отдельного intake batch с metadata-only `source_records`.
- `tools/plan_memory_intake.py` — read-only проверка и предложение маршрута.
- `tools/source_evidence_registry.py <manifest> --apply` — явная запись SourceRecord metadata в `registry/source_records.jsonl`. Без `--apply` команда ничего не записывает.
- `schemas/source_record.schema.json` — контракт SourceRecord; исходный текст и `project_id` не разрешены в записи.

Эта цепочка покрыта round-trip тестом. Она ещё не означает, что семантические кандидаты автоматически превращаются в принятую память: promotion, индексирование и полный restore pipeline остаются отдельными незавершёнными этапами.
