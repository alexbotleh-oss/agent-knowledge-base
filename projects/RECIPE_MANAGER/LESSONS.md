# RECIPE_MANAGER — уроки и отрицательный опыт

## RL-001 — Строгое сравнение названий разрушает сопоставление запасов
- **Статус:** validated as problem pattern from observed conversation; exact algorithm root cause inferred from prior assistant explanation, not independently reproduced in this transfer.
- **Симптом:** ингредиенты из рецептов не связывались с имеющимися продуктами из-за регистра, порядка слов, падежей и близких формулировок.
- **Первоначальная гипотеза из истории:** helper hv() сравнивал названия почти один к одному.
- **Профилактика:** централизованная нормализация и набор тестовых пар/непар перед функцией наличия; проверять также отрицательные пары и синонимы, не применять широкое contains-сопоставление.
- **Критические контрпримеры:** «рис» не равно «рисовая мука»; куриный фарш не должен автоматически считаться обычным мясным фаршем; явные красный/зелёный лук не сводить к репчатому.

## RL-002 — Нельзя сообщать о починке без проверяемого артефакта
- **Статус:** validated process lesson from this conversation sequence.
- **Симптом:** в переписке несколько раз объявлялись готовые HTML-файлы и проверки; затем пользователь сообщал о поломанном доступе к базе или исчезнувшем пополнении списка рецептов. Текущая передача не содержит независимых журналов тестов этих версий.
- **Вывод:** заявленные ассистентом «синтаксис без ошибок» или «готово» не доказывают функциональность списка, загрузки БД, редактирования, удаления и БЖУ.
- **Профилактика:** сохранять конкретный файл/commit, точные входные данные, результаты проверок; проверять поведение после загрузки базы, локального добавления, обновления, удаления и перезагрузки. Кодовый осмотр и синтаксический тест маркировать отдельно от функциональной проверки.

## RL-003 — Источники рецептов нельзя случайно заменить друг другом
- **Статус:** вероятная причина дефекта, описанная в последнем сообщении ассистента; пользователь жаловался на неисправный список, но исправление после жалобы в доступной истории не подтверждено.
- **Наблюдение:** ассистент сообщил, что в файле использовалось if(DB_LOADED)return DB_RECIPES, из-за чего встроенные и локально добавленные рецепты могли исчезать из списка.
- **Статус причины:** требует сверки с фактическим исходным файлом; хранить как проверяемую гипотезу до воспроизведения.
- **Профилактика:** объединять встроенные, БД и пользовательские источники с явной политикой дедупликации, не использовать скрывающий данные ранний return; тестировать добавление локального рецепта до/после загрузки БД.

## RL-004 — Проверять реальные данные, а не только отсутствие исключения
- **Статус:** переносимый по проекту урок.
- **Симптомы в истории:** список рецептов не пополнялся после добавления из базы; исчезали элементы управления удалением и отображение КБЖУ; импорт 1000.menu выдавал ошибку; Flet сообщал PopupMenuItem.__init__() got an unexpected keyword argument 'text'.
- **Что известно:** эти проблемы были сообщены в истории пользователя. Их окончательное устранение в текущей версии не подтверждено.
- **Профилактика:** проверять количество и идентификаторы рецептов до/после импорта, форму данных, UI карточки, удаление одного/нескольких рецептов, КБЖУ и реальный запуск на используемой версии Flet.

## RL-005 — Файл SQLite в браузере и API — разные режимы
- **Статус:** наблюдение об ограничении, подтверждено только логикой, описанной в сообщении ассистента; повторно в окружении не тестировалось.
- **Вывод:** прямой выбор SQLite-файла через браузерный SQL-WASM следует считать read-only, пока не доказана обратная запись в файл. Для устойчивых изменений использовать API и проверять, что изменения попали в БД.
- **Профилактика:** явно показывать пользователю активный режим (файл read-only/API writable), не обещать сохранение в исходный .db из браузера.
