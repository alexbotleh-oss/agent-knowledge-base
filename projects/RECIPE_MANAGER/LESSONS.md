# LESSONS — RECIPE_MANAGER

## L-RM-001 — Отсутствующий вспомогательный файл способен ломать запуск
- **Свидетельство:** в доступной сводке пользователь вручную восстановил `seed_data.py`, после чего `flet run main.py` работал.
- **Причина:** наличие/отсутствие файла было связано с возможностью запуска в описанном случае; полный traceback и архитектура импорта здесь не сохранены.
- **Правило:** перед запуском/упаковкой сверять manifest проекта и включение всех обязательных Python-модулей/ресурсов в рабочий каталог/артефакт.
- **Статус:** подтверждённое наблюдение в рамках конкретного проекта; не доказано, что этот файл объясняет нынешний чёрный экран.

## L-RM-002 — Версия API Flet имеет значение
- **Свидетельство:** 2026-09-27 возникла ошибка `PopupMenuItem.__init__() got an unexpected keyword argument 'text'`.
- **Вывод:** код должен соответствовать фактической версии API; нельзя переносить аргументы между версиями без проверки.
- **Правило:** записать версию установленного Flet, свериться с API этой версии и выполнить compile/import/run test. Синтаксический тест не заменяет runtime.
- **Статус:** событие ошибки подтверждено, конечный фикс по имеющимся данным не подтверждён.

## L-RM-003 — Компиляция Python не доказывает исправность APK
- **Свидетельство:** кандидат `/mnt/data/main.py` ранее прошёл `python -m py_compile`, при этом текущая Android-отладка остаётся незавершённой.
- **Правило:** отделять статические проверки, упаковку, установку и реальный запуск Android в отчёте. Для чёрного экрана нужен лог runtime и/или фактический скриншот после старта.
- **Статус:** применимое процедурное правило, выведенное из наблюдаемого различия статусов; код Android в этом сеансе не проверен.

## L-RM-004 — После изменений в данных проверять фактическое содержимое
- **Свидетельство:** в сентябре пользователь сообщал, что после изменений перестал пополняться список рецептов из БД; ранее в HTML-вариантах исчезали удаление рецепта и КБЖУ/ккал на 100 г.
- **Правило:** недостаточно отсутствия исключения или успешного рендера — проверить, что рецепт реально добавлен, БД не потеряла записи, операция удаления работает и нутриенты видны.
- **Область:** регрессии HTML-версий были историческими и не должны автоматически приписываться нынешнему Android-кандидату.
- **Статус:** исторические симптомы подтверждены сообщениями пользователя; точные исправления и финальные тесты отсутствуют в доступной выдержке.

## L-RM-005 — Изменение интерфейса без регрессии бизнес-функций
- **Свидетельство:** проект имеет множество связанных вкладок (рецепты, продукты, покупки, готовка, семейная синхронизация, «О программе»), и пользователь неоднократно просил сохранять существующие функции.
- **Правило:** для патчей UI выполнить минимум один релевантный сценарий по затронутой функции и проверку связанных данных; не объявлять всю регрессию PASS по одному экрану.
- **Статус:** проектный урок; масштаб полного автоматизированного набора тестов неизвестен.

## L-RM-006 — Hover overlay Flet: формат цвета
- **Свидетельство из сохранённой сводки:** кнопки разных базовых цветов показывали жёлтый цвет при наведении; после общего изменения overlay на ARGB-значения пользователь подтвердил, что исправление работает:
  ```python
  overlay_color={
      ft.ControlState.DEFAULT: '#00000000',
      ft.ControlState.HOVERED: '#4DFFFFFF',
      ft.ControlState.PRESSED: '#80000000',
  }
  ```
- **Правило:** если цвет всех кнопок одинаково ломается на hover, в первую очередь проверить общий overlay и формат ARGB, а не исправлять цвет каждой кнопки отдельно.
- **Статус:** подтверждено сообщением пользователя в сохранённой сводке; exact commit недоступен.


## L-RM-007 — Проверяй гипотезу о порядке инициализации навигации до новой Android-сборки
- **Свидетельство:** в переданном ответе другого чата сообщено о двух неудачных сборках и предложено проверить вызов `apply_platform_nav()` до первого `render_home()`; `on_connect` оставить дополнительным обновлением.
- **Что неизвестно:** сами логи сборок и патч не приложены; первопричина не доказана. Не установлено, когда Flet 1.0.1 предоставляет платформу и как изменение `nav.destinations` обновляет созданный UI.
- **Правило:** сначала проверить актуальный код и платформенный lifecycle, затем выполнить синтаксическую проверку и запуск на ПК; только после этого собирать APK и проверять на устройстве.
- **Критерии:** Android — 5 кнопок; ПК — 6 разделов. `recipes.db` и логику рецептов не менять. Не использовать `except Exception: pass` для скрытия ошибок определения платформы.
- **Статус:** candidate / гипотеза профилактики; исправление не подтверждено.

## L-RM-008 — Успешная упаковка не подтверждает нужное поведение навигации
- **Свидетельство:** текущий чат 2026-10-12: `py_compile` завершился без ошибки, пользователь подтвердил запуск на ПК, APK build 5 собран, но на телефоне осталось шесть пунктов навигации.
- **Правило:** отдельно фиксировать синтаксис, PC runtime, APK packaging и критерии UI на целевом устройстве. Успешная сборка не доказывает, что платформа показывает ожидаемые destinations.
- **Неудачная попытка:** переключение `nav.destinations` в `page.on_connect` не привело к требуемым пяти кнопкам в Android по сообщению пользователя.
- **Статус причины:** UNKNOWN; порядок инициализации до первого рендера — только следующая гипотеза.
- **Границы:** не связывать этот дефект с чёрным экраном без отдельного доказательства и не трогать БД/логику рецептов для исправления панели.

## L-RM-009 — Импорт и нормализацию проверяй на фактических примерах
- **Источник:** EVT-20261012-006 и события 2026-09-22.
- **Наблюдение:** пользователь сообщал о неработающем добавлении рецептов из БД, проблеме импорта 1000.menu и потере удаления/КБЖУ в отдельных HTML-итерациях.
- **Причина:** UNKNOWN; доступная история не содержит полного diff и финального набора файлов.
- **Правило:** проверять фактическую запись/повторное чтение БД, удаление, отображение КБЖУ и набор примеров ингредиентов с вариациями регистра/словоформ/порядка слов; сохранять исходную БД.
- **Статус:** candidate, confidence medium. Не переносить причинные выводы на Android/Flet без доказательств.

## L-RM-011 — Долгая упаковка без нового вывода не доказывает ни прогресс, ни зависание
- **Свидетельство:** EVT-20261012-008: Windows build после `flet clean` дошёл до `Packaging python app...` и оставался на этом сообщении примерно 10 минут. Команда проверки процессов не выполнилась корректно из-за завершающего `|`, поэтому CPU/память и изменение размера артефактов не измерены.
- **Что подтверждено:** раннее сообщение `git is not recognized` / `Unable to determine engine version` встречалось в предыдущей попытке; более поздняя попытка достигла этапа упаковки Python.
- **Что неизвестно:** почему стадия занимала время, завершилась ли она позже, появился ли APK. Не выводить зависание/успех без последующих логов и проверки файла артефакта.
- **Правило профилактики:** в отдельном PowerShell выполнять завершённые команды мониторинга без висящего pipe, сохранять результаты с интервалом, сравнивать фактические значения и журнал сборки; отмечать сборку PASS только по сообщению об успешном завершении и наличию конкретного APK.
- **Статус:** кандидатный урок, confidence high для факта ожидания и отсутствия измерения; причина задержки остаётся UNKNOWN.


## L-RM-012 — Не дублировать симптом из одного и того же скриншота как отдельный инцидент
- **Свидетельство:** при сверке текущего чата скриншот `Packaging python app...` совпадает по смыслу с уже зафиксированным `EVT-20261012-008`; независимое доказательство новой сборки/нового запуска отсутствует.
- **Риск:** отдельная запись могла бы искусственно удвоить один инцидент и исказить хронологию.
- **Правило:** сначала искать существующие события и связывать новые упоминания с ними; создавать отдельный event только при подтверждённо новом запуске, изменившейся конфигурации или новой наблюдаемой ошибке. Если хронология неполна, отметить гипотезу о совпадении и не сливать её с фактами.
- **Статус:** кандидатный урок; уверенность высокая для требования дедупликации, но тождество конкретных запусков остаётся неизвестным.
- **Источник:** EVT-20261012-009 и EVT-20261012-008.

## L-RM-013 — Проверять весь UI theme stack, а не только первую заметную панель
- **Свидетельство:** в Build39 скриншоты WHITE/DARK показали, что основная поверхность и верхняя панель переключались, а нижний NavigationBar оставался белым. Пользователь прямо уточнил, что несогласованность наблюдается по меню/разделам приложения, и указал, что локальная правка одной панели не отвечает задаче.
- **Наблюдаемая ошибка подхода:** после этого анализ был сужен до нижней панели, и был предложен Build42 без подтверждения полного аудита всех слоёв.
- **Root cause:** конкретное распределение theme state по Flet/Android chrome требует проверки кода и устройства; не считать причиной только один nav bgcolor.
- **Эффективный подход:** сначала составить карту слоёв и мест настройки темы: Android status bar/icons, app bar/title/menu, фон страницы, карточки/поля/диалоги/меню, нижний NavigationBar и Android system navigation bar. Сравнить WHITE и DARK для всех основных маршрутов и вспомогательных меню; сохранить уже принятую модель ПК/Android как отдельное платформенное требование.
- **Статус:** candidate; высокий уровень уверенности в процессном уроке, первопричина UI не установлена.
- **Профилактика:** до изменения перечислить все слои, точки настройки и проверки; после изменения выполнить визуальную регрессию полного маршрута/меню в обеих темах и свериться с исходной просьбой пользователя.
- **Источник:** EVT-20261012-010 и сообщения пользователя после скриншотов Build39.

## L-RM-014 — Сохранять проверенный scanner baseline и не считать заявленный возврат к нему доказанным
- **Свидетельство:** в Build39 пользователь подтвердил работу основных потоков нативного сканера. Старый WebView-сканер после переключения двигателя дал белый экран. Build40 был заявлен как возврат SCANNER_HTML из RecipeManager_BASELINE_20260927.py, но фактическое успешное устройство-тестирование этого варианта отсутствует.
- **Неэффективный подход:** объявлять восстановление старой реализации готовым только из-за совпадения исходного HTML или успешного py_compile/сборки.
- **Эффективный подход:** фиксировать точный baseline (путь, SHA/контрольная сумма/версия), сравнивать целый вызовной путь — источник HTML, загрузку WebView, разрешения, URL callbacks, lifecycle и возврат результата — и раздельно отмечать static/build/device PASS.
- **Статус:** candidate, confidence high по последовательности пользователя, но причина белого экрана неизвестна.
- **Профилактика:** до замены технологии открыть последнюю подтверждённо рабочую реализацию и diff; не удалять её. Проверить старый режим на устройстве отдельно от нативного сканера, затем повторно проверить native.
- **Источник:** EVT-20261012-010 и доступные сообщения/сводка Build39–Build40.

## L-RM-015 — Вода в каталоге продуктов, вода в покупках и идентичность от повторного скана — разные инварианты
- **Свидетельство:** после сообщения ассистента, что вода снова добавляется, пользователь сообщил, что повторное сканирование не находит запись и создало три отдельных пункта «Вода».
- **Ключевое различение:** пользователь требует разрешать хранение воды в каталоге продуктов; одновременно историческое правило состоит в том, что вода не должна автоматически добавляться в список покупок. Оба правила не отменяют необходимость искать/обновлять существующий продукт при повторном сканировании того же штрихкода/имени.
- **Root cause:** UNKNOWN; реализация и способ дедупликации в точном APK в этой задаче не исследовались.
- **Эффективный подход:** проверять три независимых случая: (1) сохранить воду в продуктах; (2) при расчёте ингредиентов вода не создаёт ненужную покупку; (3) два/несколько сканов одного кода не создают дубликаты, а находят ту же запись и следуют выбранному режиму ask/add/edit. Проверить как по barcode, так и по нормализованному имени/источнику записи, не меняя другие правила без причины.
- **Статус:** candidate, confidence high для воспроизведённого сообщения о симптоме; причина неизвестна.
- **Профилактика:** регрессия должна проверять БД/IDs и UI после каждого повторного скана, а не только успешный показ формы добавления.
- **Источник:** EVT-20261012-010 и пользовательское сообщение: после повторного сканирования было три отдельных «Вода».

## L-RM-016 — Вести контрольную карту достижений/зависимостей и перепроверять итог с исходным запросом
- **Свидетельство:** пользователь прямо потребовал дерево зависимостей и достижений, устойчивые маркеры «сделано/не сделано», сохранение старых успешных решений и повторную сверку результата с первоначальным запросом.
- **Наблюдаемая ошибка процесса:** ответы фиксировали первый заметный дефект и слишком рано предлагали правку, не проверяя соседние слои, предыдущие рабочие варианты и регрессию уже исправленных сценариев.
- **Эффективный подход:** до изменений держать карту компонентов/зависимостей, матрицу статусов (confirmed / claimed / not verified / failed / blocked), canonical baseline и ссылки на evidence. После каждого патча проверить как целевой случай, так и все зависимые ранее PASS-сценарии; затем сверить итог с каждым требованием пользователя.
- **Статус:** validated as explicit user process requirement; confidence high. Не подразумевает, что такая автоматическая система уже реализована.
- **Профилактика:** не закрывать задачу по одному положительному тесту и не повторять проверку уже закрытого дефекта без причины; но каждый связанный патч обязан запускать определённый регрессионный набор. Хранить причины неудач и доказательства старых побед.
- **Источник:** EVT-20261012-011.



## L-RM-017 — Проверять именно выданный архив и реальную команду потребителя
- **Свидетельство:** 2026-10-12 был выдан архив `RecipeManager_Build43_3CAM_VERIFIED_SOURCE_20260929.zip` с утверждением, что путь зависимости исправлен. Последующая инспекция самого архива показала, что `pyproject.toml` по-прежнему содержал `flet-barcode-scanner @ ./flet_barcode_scanner_ext`. Пользователь очистил папку, скопировал архив и запустил `flet build apk --verbose`; pip завершился с `Invalid URL './flet_barcode_scanner_ext': No scheme supplied.`.
- **Наблюдаемая ошибка процесса:** утверждение об исправлении архива было сделано без достаточного подтверждения содержимого конечного файла и его фактического поведения при использовании Flet.
- **Подтверждённое пользовательское правило:** перед выдачей файла/архива обязательно проверять именно сохранённый результат; после изменения его открыть/прочитать заново, проверить зависимости и всю цепочку исполнения. Если пользователь уже выполнил инструкцию и сбой повторился, сначала проверить собственный артефакт/инструкции, не заставляя пользователя повторять процедуру без доказательств проблемы с его стороны. Каждая ошибка должна усиливать процесс проверки.
- **Профилактика:** (1) создать и сохранить артефакт; (2) перечитать именно сохранённый файл/архив; (3) проверить SHA-256 и состав; (4) проверить конфигурацию, локальные зависимости и переносимость; (5) воспроизвести точную команду/парсер потребителя на подготовленном комплекте насколько позволяют средства; (6) проверить callback/API/entrypoints и runtime-цепочки; (7) только затем передавать файл, перечисляя непроверенные стадии.
- **Статус:** validated — прямое правило пользователя; факт повторного сбоя подтверждён присланным логом и последующей инспекцией архива.
- **Границы:** этот урок не доказывает существование исправленного нового APK. Текущая задача — перенос памяти; приложение и APK здесь не менялись.
- **Источник:** EVT-20261012-012; сообщение пользователя с логом `flet build apk --verbose` от 2026-10-12.


## L-RM-018 — Сверять структуру памяти с фактическим деревом
- **Свидетельство:** на HEAD ветки переноса LESSONS.md содержит L-RM-001..017, а путь `projects/RECIPE_MANAGER/lessons.jsonl` отсутствует, хотя ранние handoff упоминали этот файл и сообщали о его валидации.
- **Предотвращаемая ошибка:** полагаться на старое описание структуры или отчёт о предыдущей проверке вместо фактического дерева текущего HEAD.
- **Правило:** перед чтением/записью памяти проверить реальное дерево целевой ветки; считать файл существующим лишь после подтверждения пути и чтения содержимого. При расхождении зафиксировать его; не создавать пустой или заново реконструированный журнал без подтверждённого формата/схемы.
- **Статус:** наблюдение о текущем дереве и прежних ссылках подтверждено; причина отсутствия файла неизвестна.
- **Источник:** EVT-20261012-013, фактическое дерево ветки и LESSONS.md/HANDOFF.md.


## L-RM-019 — Регрессионно проверять каждый HTML-кандидат относительно рабочего эталона

- **Свидетельство:** пользователь сообщил, что в последнем HTML-кандидате перестало работать добавление рецептов из БД и пропало КБЖУ; затем указал на отсутствие удаления рецепта и отображения калорийности/БЖУ, которые присутствовали в эталоне `index_db_path(5).html`. В доступной истории было несколько разных HTML-кандидатов, однако подтверждённый пользовательский runtime PASS для последнего файла отсутствует.
- **Ошибка процесса:** объявлять файл исправленным по синтаксической проверке/анализу кода или по наличию ссылки, не сверив конечный сохранённый файл и ключевые регрессионные сценарии. Сохранение новых правил нормализации не компенсирует потерю уже работающих возможностей.
- **Правило:** считать конкретную подтверждённую версию `index_db_path.html` эталоном поведения; сравнить целевой файл с ним по списку функций и после записи перечитать/проверить именно конечный артефакт. Минимальная регрессия: импорт/добавление из SQLite, КБЖУ на 100 г (ккал/белки/жиры/углеводы), удаление рецепта из поддерживаемого источника, сохранение изменений БД/API, редактирование, ингредиентное сопоставление и обработка отсутствующих nutrition values.
- **Не считать проверкой:** наличие функции в тексте, JavaScript syntax PASS, наличие sandbox-ссылки или словесное «готово». Это не доказывает runtime и persistence.
- **Статус:** пользовательская регрессия и процессный урок подтверждены; root cause и исправленность последних файлов не установлены.

## L-RM-020 — Входной и выходной контроль пакета должен воспроизводить путь реального потребителя

- **Свидетельство:** после `EVT-20261012-012` пользователь снова запустил `flet build apk --verbose` в `C:\RecipeManager_FIX_PLUS`. Flet обнаружил entrypoint и создал app shell, но установка `flet-barcode-scanner @ ./flet_barcode_scanner_ext` остановилась с `Invalid URL './flet_barcode_scanner_ext': No scheme supplied`. Ассистент признал, что фактическая установка extension способом, которым его потребляет Flet, не была проверена до объявления кандидата готовым.
- **Ошибка процесса:** проверка не включала реальный шаг установки зависимости. Целостность ZIP, наличие entrypoint или визуальная проверка `pyproject.toml` не доказывают install/build PASS.
- **Root cause ошибки pip:** **UNKNOWN**. По одному логу нельзя заключить, отсутствует ли каталог расширения или проблема связана с его содержимым/форматом локальной ссылки/путём сборки.
- **Обязательное правило:** на входе перечислить источники, зафиксировать canonical baseline, проверить обязательные файлы и direct/transitive dependencies. В change/package manifest перечислять added/modified/excluded files и обосновывать каждое исключение. На выходе перечитать именно сохранённый артефакт, сверить SHA-256 и дерево файлов с manifest, проверить потери/дубликаты, `pyproject.toml` и dependency closure. Затем воспроизвести реальную установку/сборку потребителя либо явно отметить её NOT RUN/NOT VERIFIED и не объявлять пакет готовым.
- **Жёсткий STOP:** любой обязательный FAIL/BLOCKED запрещает выдавать пакет как готовый. Если безопасное исправление не следует из доказательств или отсутствует источник, точно описать блокировку и запросить недостающий материал. Не удалять зависимость, менять архитектуру или подменять baseline ради прохождения сборки.
- **Change log:** для каждого патча/пакета указывать файл(ы), строки или уникальный контекст, состояние before/after, причину, связанные event/lesson, затронутые зависимости и выполненные проверки. Если строки сдвигаются, сохранять уникальный контекст.
- **Статус:** требование пользователя и процессный сбой подтверждены; это не означает, что автоматический gate уже реализован.
- **Источник:** `EVT-20261012-015`, пользовательский PowerShell log 2026-10-12 около 19:49:53–19:50:06 и явное требование пользователя.

## L-RM-021 — UI controls that highlight but do not apply require tracing the existing event chain

- **Свидетельство:** пользователь сообщил, что шторки категорий и сортировки продуктов открываются и показывают варианты, но нажатие лишь визуально выделяет элемент либо шторку; список не фильтруется и не сортируется. После нескольких попыток core33/core34 пользователь снова сообщил об отсутствии результата.
- **Подтверждённый соседний результат:** после фильтрации Покупок единицы отображались латиницей; пользователь подтвердил исправление этого отдельного визуального дефекта в core32. Не смешивать его с неработающим выбором в Продуктах.

- **Приёмка:** категория должна реально уменьшать список; сортировка должна менять порядок; после закрытия шторки результат должен сохраняться. - **Статус:** процессный урок подтверждён повторными пользовательскими сообщениями; причина ошибки в UI не установлена. Runtime UI не проверялся в задаче переноса памяти.
- **Источник:** EVT-20261012-016; пользовательские скриншоты/сообщения после core33/core34 и ограничение memory-only задачи.
