# DECISIONS — RECIPE_MANAGER

## DEC-RM-001 — Android-отладка раньше редизайна
- **Дата:** 2026-10-12
- **Статус:** принято пользователем
- **Решение:** не изменять интерфейс Android и не добавлять новые функции, пока не завершена отладка текущей сборки.
- **Причина:** сначала обеспечить рабочий запуск приложения, затем возвращаться к визуальным улучшениям.
- **Основание:** непосредственное сообщение пользователя: «нет исправление интерфейса андроид, к этому мы вернемся после его отладки».
- **Последствие:** диагностика чёрного экрана, сборка/установка и проверка основных сценариев имеют приоритет.

## DEC-RM-002 — Текущие данные защищены
- **Дата:** историческое проектное соглашение; точная дата не установлена
- **Статус:** действующее ограничение, отражённое в контексте работы
- **Решение:** сохранять БД, пользовательские файлы, `seed_data.py`, настройки сборки и уже работающие функции при исправлениях.
- **Причина:** ранее сообщалось, что отсутствие `seed_data.py` влияло на запуск Flet, а также были регрессии данных и функций в итерациях приложения.
- **Проверка:** подтвердить состав каталога и сделать копию перед изменениями; после патча выполнить регрессию.

## DEC-RM-003 — Один диагностический патч за раз
- **Дата:** следует из повторяющихся требований к последовательной отладке; конкретная дата принятия не установлена
- **Статус:** рабочий принцип
- **Решение:** установить симптом и вероятную причину, сделать минимальное изменение, проверить результат и только затем переходить к следующей зоне.
- **Ограничение:** это не разрешает процессуальные циклы «проверить проверку»; проверка должна подтверждать критерий и давать доказательство.

## DEC-RM-004 — Сканирование товара отложено
- **Дата:** 2026-10-12, точный штамп исходного обсуждения не установлен
- **Статус:** предложенная идея, не реализовывать сейчас
- **Решение/контекст:** обсуждалась потенциальная поддержка DataMatrix «Честного знака», EAN-13 и EAN-8, извлечение GTIN, локальное сопоставление с товаром и внешняя база.
- **Основание отложить:** текущая задача — отладка Android; улучшение UI и дальнейшие возможности после неё.
- **Не считать:** это решение об архитектуре и реализации не принято как активная задача. API, таблица `product_codes` и кнопка сканирования остаются предложениями, а не реализацией.

## DEC-RM-005 — Статусы проверок должны быть честными
- **Статус:** обязательство по рабочему процессу
- **Решение:** синтаксическая проверка Python не считается подтверждением успешной Android-сборки/запуска; сборка не считается рабочей без запуска на устройстве или равноценного доступного подтверждения.

## DEC-RM-006 — Явные доменные эквивалентности ингредиентов
- **Дата:** восстановлено из доступной истории проекта 2026-09-22…2026-10-12.
- **Статус:** пользовательская спецификация; соответствие реализации не проверено.
- Нормализация должна учитывать регистр, ё/е, порядок слов и грамматические формы, но использовать явные правила по типам продукта и отрицательные пары, чтобы избегать ложных совпадений.
- Примеры: «лук»/«белый лук»/«репчатый лук» → репчатый; красный и зелёный лук остаются отдельными; общий рис → длиннозёрный, рис для плова/пропаренный → пропаренный; не сопоставлять рисовую муку/рисовое масло с рисом; яйца/яйцо/куриное яйцо; подсолнечное/растительное масло; говядина/мясо говяжье; свинина/мясо свиное; учитывать исключение куриного фарша при общем мясном фарше.
- **Критерий:** сохранять исходное отображаемое название рецепта отдельно от нормализованного ключа поиска; проверять положительные и отрицательные пары и фактическое end-to-end добавление рецепта.
- **Источник:** доступный контекст RECIPE_MANAGER и EVT-20261012-014; более ранняя отдельная ветка PR #21 содержала пересекающиеся EVT IDs, поэтому не переносить её номера событий без сверки.

## DEC-RM-007 — Core Lite lane D и раздельные статусы подтверждения
- **Дата источника:** 2026-09-30…2026-10-01 по доступной сводке.
- **Статус:** ранее принятый диагностический принцип, актуальность baseline требует проверки.
- Использовать цепочку reference → read → one logical patch → build → device test → evidence; не менять JNI/mobile_scanner/WebView/permissions наугад.
- Разделять CODE_CONFIRMED → APK_BUILD_CONFIRMED → DEVICE_VERIFIED. Targeted py_compile не означает полный compile; build success не означает корректный UI/device runtime.
- **Источник:** историческая память PR #17, EVT-RM-20260930-001/002 и EVT-RM-20261001-001..004. Исходные ZIP/diagnostics не перечитаны в текущем rollup.

## DEC-RM-008 — Редактирование срока годности партии и расположение добавления продукта
- **Источник:** EVT-RM-20261002-001; прямое сообщение пользователя 2026-10-02 и более поздняя в тот же день контрольная матрица в Library.
- **Статус:** требование подтверждено пользователем и отражено в контрольной матрице; реализация не проверена.
- **Требование:** пользователь должен иметь возможность исправить срок годности уже сохранённой партии; «Добавить продукт» должно быть размещено над списком. Сводка изменений `RecipeManager_сводка_изменений_FIX6_V20_V21_N99.xlsx` помечает UI-05 как `CHANGE / USER`, P-07 как `CHANGE / USER + AUDIT`, а отдельное редактирование партии P-10 как `TODO`.
- **Целевая модель:** срок годности относится к партии продукта, а не только к общему названию продукта; матрица v1.2 отмечает партии как `PARTIAL`. Это проектное требование, а не подтверждение текущей схемы или работающего edit-path.
- **Неизвестно:** причина невозможности редактирования в фактическом коде; наличие полной модели партий в текущем Flet-кандидате; прошёл ли сценарий ручной проверки.
- **Проверка при возобновлении разработки:** отдельно проверить редактирование существующей партии/expiry и положение кнопки относительно V20; после изменения сохранить данные, перечитать их и повторить регрессионный сценарий.
- **Ограничение:** в текущей задаче только перенос памяти; код/БД приложения не изменять.
## DEC-RM-009 — Исторический этап HTML-макета перед переносом во Flet
- **Дата источника:** 2026-10-01…2026-10-02.
- **Статус:** подтверждённое историческое решение о порядке работ на тот момент; его текущая активность не предполагается автоматически.
- **Решение:** сначала инвентаризировать функции и проверить окна, бизнес-логику, зависимости и регрессии в HTML-макете; переносить проверенное поведение во Flet после завершения этой фазы.
- **Иерархия источников:** V20 задаёт внешний вид/расположение; текущий Flet-проект — функциональный образец; FIX6, V21, аудит и master map служат для сверки сканера, функций и зависимостей.
- **Сканер:** старый сканер исключён, нативный сканер сохранён как референс для Flet.
- **Граница проектов:** данный HTML-макет был временным этапом N99/RECIPE_MANAGER. Не смешивать его с отдельным B77 HTML/WMA/PWA-проектом для iPhone.
- **Последующее изменение приоритета:** DEC-RM-001 от 2026-10-12 ставит отладку текущей Android-сборки перед UI-редизайном. Это более поздний ближайший приоритет; он не доказывает, что исторический HTML-макет был завершён или что все его требования перенесены.
- **Источник:** EVT-RM-20261001-005; сообщения пользователя e236dd8a-b2f5-4824-ae2d-fe6bc8548d60, bbb2177a-9480-425c-b918-62db8d9d8f44, bbb21081-42c0-4afe-95e0-5903b685cbd5, bbb2144b-2996-44e4-a362-f75cc39047c9 и c5d01ab5-ce18-44c4-9dbc-4b88694e08ea.
