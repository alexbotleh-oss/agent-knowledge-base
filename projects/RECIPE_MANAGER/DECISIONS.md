# DECISIONS — RECIPE_MANAGER

## DEC-RM-001 — Android-отладка раньше редизайна
- **Дата:** 2026-10-12
- **Статус:** принято пользователем
- **Решение:** не изменять интерфейс Android и не добавлять новые функции, пока не завершена отладка текущей сборки.
- **Причина:** сначала обеспечить рабочий запуск приложения, затем возвращаться к визуальным улучшениям.
- **Основание:** непосредственное сообщение пользователя: «нет исправление интерфейса андроид, к этому мы вернемся после его отладки».
- **Последствие:** диагностика чёрного экрана, сборка/установка и проверка основных сценариев имеют приоритет.

## DEC-RM-002 — Текущие данные защищены
- **Дата:** историческое проектное соглашение; точная дата не установлена
- **Статус:** действующее ограничение, отражённое в контексте работы
- **Решение:** сохранять БД, пользовательские файлы, `seed_data.py`, настройки сборки и уже работающие функции при исправлениях.
- **Причина:** ранее сообщалось, что отсутствие `seed_data.py` влияло на запуск Flet, а также были регрессии данных и функций в итерациях приложения.
- **Проверка:** подтвердить состав каталога и сделать копию перед изменениями; после патча выполнить регрессию.

## DEC-RM-003 — Один диагностический патч за раз
- **Дата:** следует из повторяющихся требований к последовательной отладке; конкретная дата принятия не установлена
- **Статус:** рабочий принцип
- **Решение:** установить симптом и вероятную причину, сделать минимальное изменение, проверить результат и только затем переходить к следующей зоне.
- **Ограничение:** это не разрешает процессуальные циклы «проверить проверку»; проверка должна подтверждать критерий и давать доказательство.

## DEC-RM-004 — Сканирование товара отложено
- **Дата:** 2026-10-12, точный штамп исходного обсуждения не установлен
- **Статус:** предложенная идея, не реализовывать сейчас
- **Решение/контекст:** обсуждалась потенциальная поддержка DataMatrix «Честного знака», EAN-13 и EAN-8, извлечение GTIN, локальное сопоставление с товаром и внешняя база.
- **Основание отложить:** текущая задача — отладка Android; улучшение UI и дальнейшие возможности после неё.
- **Не считать:** это решение об архитектуре и реализации не принято как активная задача. API, таблица `product_codes` и кнопка сканирования остаются предложениями, а не реализацией.

## DEC-RM-005 — Статусы проверок должны быть честными
- **Статус:** обязательство по рабочему процессу
- **Решение:** синтаксическая проверка Python не считается подтверждением успешной Android-сборки/запуска; сборка не считается рабочей без запуска на устройстве или равноценного доступного подтверждения.

## DEC-RM-006 — Не считать обработчик on_connect достаточным для конфигурации начальной навигации
- **Дата:** 2026-10-12
- **Статус:** наблюдение о неудачной попытке; первопричина unknown
- **Наблюдение:** после применения варианта, который устанавливал `nav.destinations` в `page.on_connect`, ПК-запуск и APK-сборка завершились успешно, но пользователь сообщил, что в Android APK всё ещё шесть кнопок.
- **Вывод:** `on_connect`-вариант не достиг критерий Android=5 в наблюдавшейся сборке. Это не доказывает почему.
- **Следующая гипотеза:** проверить конфигурацию платформенной навигации до первого `render_home()`; приписывать ей успех только после фактической проверки на устройстве.

## DEC-RM-007 — Не считать прежние HTML/SQLite-регрессии исправленными без артефакта и проверки
- **Дата фиксации:** 2026-10-12; исторические сообщения относятся преимущественно к 2026-09-22.
- **Статус:** правило достоверности памяти.
- **Основание:** история подтверждает пользовательские сообщения о неработающем добавлении из БД, потере удаления/КБЖУ и ошибке импорта, но не содержит полного diff финальных файлов.
- **Решение:** хранить их как исторические инциденты с неустановленной причиной; не объявлять исправление подтверждённым по имени файла или факту последующей итерации.

## DEC-RM-008 — Food/non-food assignment must be an explicit working user control
- **Дата:** 2026-10-12
- **Статус:** explicit user requirement; implementation unresolved
- **Требование пользователя:** on manual product entry, the user must be able to choose a non-food category/classification; alternatively, the existing product UI must expose a functional checkbox/toggle to reclassify an existing item as non-food. The user reported that the current checkbox does not work.
- **Expected behavior:** a household item such as “Туалетная бумага” must be classified as non-food by explicit user action, remain discoverable in the all-items view, and not appear in the food-only view. The selected classification must persist after save/reload and affect filtering consistently.
- **Avoid:** assuming that changing a text category such as “Прочее” automatically decides food/non-food; claiming category editing is fixed without testing create, edit, persistence and both views.
- **Evidence:** direct clarification in this chat, following failed v18/v19 category attempts.
- **Status note:** this is a product requirement, not evidence that v19 implements it.
